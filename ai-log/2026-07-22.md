## トランジション方針（議論メモ・spec 未反映）
- 「ハッシュルーター＋DOM 差し替え」でルーティング手段としては妥当。パフォーマンスは 3 展示規模では論点にならない。
- 「View Transitions がスマホで効かない」という前提は 2026 時点では古め。**iOS Safari 18（2024/9）・Android Chrome とも対応**。非対応は古い端末の裾野のみ。VT は非対応時に「アニメ無しで即差し替え」に自動フォールバックする設計（サイトは壊れない）。
  - ※対応状況は記憶ベース。依存を決める前に caniuse で最新確認が望ましい。
- ただし演出がサイトの「キモ」なので、即差し替えフォールバックだと非対応端末で体験が丸ごと消えるのが惜しい。→ **役割で二段構え**にする方針で合意:
  - **劇場型の派手な演出（ワープ / 幕の開閉 / ハコの飛び出し）** … VT に依存しない**自前オーバーレイ**（CSS / Web Animations）。**全端末で動く**。作り込みも自由。
  - **共有要素モーフ（Gallery Icon → Focus への連続移動）** … **View Transitions を対応環境でのみ enhancement**。非対応ならモーフだけ省略、オーバーレイ演出は残るので体験は保たれる。
  - VT 一本足には**しない**。
- この方針は本人判断で **spec-and-plan.md への反映は見送り**（ログにのみ記録）。

## スタック再検討 → Svelte へ切替（経緯）
Phase 1 の diff を Zed でレビュー中に本人から違和感。3 点が顕在化:
1. `views.ts` の**文字列テンプレート＋手動エスケープ**の記述性が悪い（→ component で書きたい）。
2. **ハッシュルーティングは Pages に載せるための妥協**で必然性が薄い（→ 素のクリーンパスにしたい）。
3. 本サイトの核心はトランジション。**DOM を保持したまま遷移する SPA 的アプローチ**が向く。

検討の流れ:
- **Astro** も候補に（旧サイトで使用実績）。静的プリレンダでクリーンパス、ClientRouter で VT 標準対応と好相性。ただし MPA 基盤なので「消えない常駐要素／連続する世界」を強く求めると `transition:persist` 等でやや窮屈になりうる、という分岐を確認。
- トランジション連続性を優先し **SPA 的アプローチ**へ傾く。
- 発想の整理: この用途は「UI フレームワーク」より「**トランジション/アニメエンジン**」の選択が主役。UI 側は *DOM を壊さず enter/exit を寄越す* ならよく、**シェーダは常に canvas＋rAF＋GLSL でフレームワーク非依存**。→ 器（ビュー/ルーター）と演出（エンジン）を分離して考える。
- 器の最終候補は **Svelte vs Solid**（自作マイクロ層も俎上に）。
  - **Solid**: JSX(TSX)＋signals（uniform 供給に good）。ただしトランジションは自前寄り。
  - **Svelte**: `transition:`/`animate:`(FLIP)/**`crossfade`（共有要素モーフ）**が言語ビルトイン。**トランジションが主役**の本件で有利。Svelte 5 runes で反応性も担保。宣言的 WebGL は **Threlte** が成熟。
  - **自作**: ポートフォリオのブランド（手書き志向）とは合うが、リアクティビティ自作の罠がある。要不要の分岐は「各ルートが基本静的か（＝反応性不要）」。
- **結論: Svelte を採用**（本人合意）。シェーダ欲は canvas 島＋GLSL で問題なく満たせる。

## ルート遷移演出（View Transitions）
体験のキモ。ここからはフェーズ厳密より微調整ベースで進める方針に切替。

- **方式**: SvelteKit `onNavigate` + `document.startViewTransition`。非対応ブラウザは即時遷移にフォールバック（芯の遷移・戻り・中央寄せは全環境で動作、演出だけ enhancement）。
- **共有要素モーフ**: title-caption に作品ごとの `view-transition-name`（`title-<id>`）を付与し、Gallery↔Focus で同要素が移動。Focus では `transform: scale(1.5)`（em 実サイズ版も試したが、静止時のキレ差は体感できず・モーフ純度で transform が勝るため transform 採用）。
- **dive/rise ズーム**: Gallery→Focus は index 全体をクリック Icon 中心に拡大フェード、Focus→Gallery は逆。原点は CSS 変数 `--vt-x/--vt-y`。
- **「1枚だけモーフ」制御**: 全タイトルに名前があると非対象がその場でフェードしてしまうため、対象1枚だけ名前を残し他は一時 `none`（root ズームに含める）→ 遷移後に復元。
- **詳細キャプション**: `view-transition-name: details` で `blur→くっきり` の「にじみ出る」入場。
- **Introduction↔About**: 顔タイポに `view-transition-name: face`。index↔about で顔が残って周囲が入替。dive/rise 時だけ名前を外して root ズームに含める。
- **戻り導線**: Focus の × を `{元Galleryルート}#{id}` に（`nav.svelte.ts` で from を保持）。戻り先で該当カードを中央スクロール（`afterNavigate` + rise 時に原点も再アンカー）。Exhibit に実 `id` を付与（プリレンダのフラグメント検証 & 非 VT 時のフォールバック）。
- **About カードにも ×**（Home へ）。`.close` を `.caption-card .close` に一般化して Focus と共通化。
- **コード整理**: 遷移ロジックを `src/lib/transition.ts` に集約。コンポーネントは `onNavigate(routeTransition)` / `afterNavigate(centerHashExhibit)` / `onclick=markExhibitOrigin` を繋ぐだけに。`onNavigate` の Promise ハンドシェイクは `Promise.withResolvers()` で平坦化。

## 顔位置の固定・中央ドリフト・戻りのカード中央着地
- **顔位置を index/about で固定**: これまで「顔＝トップ〜下部キャプション間を flex:1 で中央寄せ」だったため、キャプション高さ（index=挨拶文で高い / about=00 へのへのんで低い）の差で縦位置がズレていた。→ `.introduction` の flex をやめ、**face-area を絶対配置**（`top:0 / bottom:60px` の領域で中央寄せ）、キャプションも絶対配置の左下に。顔の縦位置は `bottom` 一箇所で調整（現 60px）。
- **dive/rise に中央ドリフト**: これまで拡大＋フェードのみ。ズームと同時に**アイコンを画面中央へ並進**（`translate(--vt-dx,--vt-dy) scale`）。移動量 = (画面中央 − アイコン中心) × DRIFT。方向は自然に中央向き。Gallery は縦中央寄せで dy が小さいため **縦だけ強め**（`DRIFT_X=0.4 / DRIFT_Y=0.6`）。
- **戻りのカード中央着地**（スクロール問題の決着）:
  - 位置決めは **CSS `scroll-margin-top: calc(50vh - 150px)`**（`scrollIntoView` の block:start が尊重）。中央の座標計算を JS でしない。
  - 効かない原因は**スクロール復元**（リロード=ブラウザ / SPA=SvelteKit）が上書きするため。→ 止めにいかず、**復元より後に後出しで再スクロール**して勝つ:
    - `afterNavigate` + `requestAnimationFrame(scrollHashIntoView)`（リロード・SPA 両対応）。
    - rise の VT コールバック内でも直接 `scrollHashIntoView()`（ズームのスナップショットを中央着地状態で撮る）＋ `clearOrigin()` で**ズームは中央から**。
  - 補助: Focus 戻りリンクに `data-sveltekit-noscroll`（SvelteKit の復元を止める）。
  - 教訓: **復元と戦って止めるのは脆い。rAF で後出しし、位置は scroll-margin に任せる**のが堅牢＆ジャック感が最小。
  - 既知の懸念: ちらつきの可能性（実機ではぱっと見問題なし。要監視）。

## 戻り導線の再検討 → シンプル化に着地（長い探索の結論）
上の「後出し再スクロール」方式はやはり脆く、色々試した末に**シンプルな形へ収束**した。

- **試して捨てたもの**（すべて逃げ or 脆さ）:
  - `history.pushState` で戻り先 `/#id` を仕込む → SvelteKit のシャロールーティング用途外で履歴が壊れ、全 back が悪化。廃止。
  - `afterNavigate`+rAF の後出し再スクロールで復元に勝つ → タイミング依存で脆い。廃止。
  - `onclick` で `<a>` を握り潰して `goto(replaceState)` → ハック。→ SvelteKit の宣言的 `data-sveltekit-replacestate` に一度置換 → さらに **push/replace を気にせず素リンクで十分**と判断し撤去。
  - **scrollspy**（scroll→`#` 追従）→ 中央着地の副産物を無理に URL 反映する「逃げ」。`IntersectionObserver` で綺麗に書き直したが、本質でないので**丸ごと撤去**。
- **最終形（現在）**:
  - **戻り = 素の `<a href="{nav.from}#{id}">`**（× / タイトル）。`#id` ＋ CSS `scroll-margin-top` の**ネイティブスクロール**で中央着地。JS スクロール操作ゼロ。
  - **rise のズーム原点**は「戻り先カードの実位置」から算出（左右ドリフトが残る＝フォールバックも兼ねる）。
  - Focus は**普通のページ（push 遷移）**として扱う。
- **概念的な結論（重要）**:
  - 「URL に状態を反映」＋「ブラウザ戻るでその状態を辿れる」は **history API だけでは両立不可**（後者は history エントリの存在そのものが仕組み）。両取りは Navigation API で戻るを intercept するしかないが、対応ブラウザ都合で重い → **今回はやらない**。
  - 割り切り: **× / タイトル経由は中央着地、ブラウザ/マウスの戻るは標準どおり「元居た位置に戻る」**。これで妥当とする。

## Introduction（index↔about）をスクロール＋CSS 入場に
- ヘッダー About（Gallery まで下げた後に出る）は、フェード/ズームより **「下→上へスクロール」** が素直、という判断。
- **重要な制約**: View Transitions は遷移中ビューポートを**凍結**するため、**VT とスムーススクロールは併用不可**。→ index↔about は **VT を切る**（`routeTransition` で `/`↔`/about` の toggle を検出して return）。
- 実装:
  - ヘッダー About = 位置維持で `/about` へ（`goto(..., { noScroll: true })`）→ `scrollTo({ top: 0, behavior: 'smooth' })`。Gallery は index/about で同一なので、スクロールで自然に About イントロが現れる。
  - キャプションの blur/fade は **VT ではなく通常 CSS アニメ**で（スクロールと共存させるため）。About 右上カード＝`about-card-in`（blur）、タイトル「00 へのへのん」＝`intro-fade-in`（fade）。about→index の戻りは index 挨拶（`.text-caption`）も `intro-fade-in` で対称に。
  - 顔モーフは index↔about では無し（顔は同一グリフで実質見えない）。gallery↔focus の VT・顔処理は不変。

## Introduction タイトル演出：VT の限界理解 → テキスト内容 morph へ方針転換
「単なるフェードじゃなく、introduction のテキストがタイトルへ**変化していく**（相互性あり）」を目指す中で、VT の仕組みを掘り下げた。

> ※ この後さらに改定。「index↔about をそもそもページ遷移にしない（query param モード切替）」に着地 → 最下段「index↔about を query param のモード切替へ」参照。morph 自体は継続だが、`onNavigate` の Promise ハンドシェイクは不要になる。

- **VT の実体**: `startViewTransition` は「旧状態を静止画スナップショット化 → DOM 更新 → 新状態をキャプチャ → 擬似要素ツリー（`::view-transition-group/old/new`）を重ねてアニメ → 剥がす」。
  - 名前ごとの group は**フラットな兄弟**として並列。名前付き要素は親から引っこ抜かれるので**親グループの変形を受け継がない**（＝ `keepOnlyTitle` で名前を出し入れしてた理由）。ネストは新プロパティ `view-transition-group`（L2, Chromium 新しめ）で可能。
  - `old` は静止画、`new` は**ライブ**。→ 新要素で JS/CSS アニメが動けば遷移中も映る（当初「VT でスクランブル不可」と言ったが**誤り**。不可なのは*ビューポートのスクロール*の方）。
  - ただし VT が扱えるのは結局**スナップショットのクロスフェード＋位置/サイズ補間**。「文字を1文字ずつ内容置換していく」は VT の仕事ではない。
- **ユーザーの本当の要望**: フェード（旧新の重ね消し）ではなく、**1 要素の `textContent` が文字数を減らしながら書き換わり、最終的にタイトルになる**。スクランブルも不要。
- **結論＝方針転換**: index↔about は **VT を使わず、JS でテキスト内容を morph** する。
  - `onNavigate` の返り Promise が解決するまで DOM 差し替えは待たれる → **今表示中のキャプション `<p>` を greeting↔title へ morph してから差し替え**れば継ぎ目なし。
  - 挨拶カードとタイトルカードを**同一マークアップ `.intro-caption-card`** に統一（差し替えの瞬間を無変化に）。`width:max-content`＋左下固定なので**テキストが縮めば箱も自然に縮む**（VT の箱モーフ不要）。

## VT×テキスト morph の事例調査（相談の裏取り）
「VT でテキスト内容の変化」を諦める前に、事例と「擬似要素を JS で無理やり触れないか」を調査した。

- **VT でテキスト内容 morph の事例は存在しない**（仕様上不可能）。VT の守備範囲は「スナップショットのクロスフェード＋group の位置/サイズ補間」まで。文字単位はどの解説でも守備範囲外と明言。
- **擬似要素 `::view-transition-*` は本物の DOM ノードではない**: `querySelector` 不可・`textContent` 無し。内容書き換え方向の JS 介入は原理的に不可能。
- 公認の JS 介入は 2 つだけ:
  1. **WAAPI の `pseudoElement` オプション**（MDN 公式手法）: `documentElement.animate(kf, { pseudoElement: '::view-transition-new(name)' })`。`transition.ready` 後。ただし transform/opacity/clip-path 等の CSS アニメ可能プロパティのみ。
  2. **`::view-transition-new` はライブな DOM 領域**（old だけが静止画）→ 遷移中に*本物の要素*の textContent を JS で書き換えれば new 越しに映る。将来 gallery↔focus で「移動しながら文字も変わる」をやるならこれ（old の即フェードアウト調整が要る）。今回の index↔about には不要。
- テキスト内容が変わる演出の既存事例は**全部 JS で textContent を書き換える系統**: GSAP TextPlugin（`type:"diff"` で差分だけアニメ、`padSpace` 等、自作 morphText と同じ問題意識のオプション群）、shiki-magic-move（トークン分解→diff→共通トークンは FLIP 移動。Keynote Magic Move の Web 実装。共通文字を"動かしたい"欲が出たらこの方式）。
- **結論**: 「文字の内容変化は JS の仕事、VT は箱の移動の仕事」で業界的にも完全に住み分け。JS morph への転換は王道。

## index↔about を query param のモード切替へ（方針決定・実装は次回）
JS morph 実装を進める中で「**そもそもページ遷移として作るべきでない**」に気づき、方針決定。about は「場所」ではなく **index の表示モード**（Gallery は完全同一、変わるのはキャプションとヘッダーだけ）。

### 検討の経緯
- **route group ＋常駐レイアウト案**（`(intro)/+layout.svelte` に IndexView、`/about` 維持）: 動くが、ページコンポーネントが空シェルになり SvelteKit の木目（ページ内容はページが描く）に逆らう。URL の見た目と about のプリレンダが利点だったが不採用。
- **hash 案**（`/#about`）: `#id`（Exhibit アンカー・戻り中央着地）と衝突するため却下。
- **query param 案（採用）**: SvelteKit は**同一ルート内ナビゲーション（query のみ変化）でページコンポーネントを破棄しない** → DOM 保持がフレームワークの素の挙動で手に入る。ルート 1 個・空シェル無し・レイアウト吸い上げ無し。意味論的にも「path=場所 / query=同じ場所の表示状態」で about=モードの枠組みに一番忠実。ハック剥がし路線の終着点。

### 決定事項（実装者向け）
1. **`/about` ルートは削除**。about 状態は **`/?about`**（素朴なフラグ、値なし）。
2. **リンク**: 顔 `.face-link`・ヘッダー About → `href="?about"`、About カードの × / caption → `href="/"`。`data-sveltekit-noscroll` は維持。ヘッダー About の `scrollTo({top:0, smooth})` も維持。
3. **IndexView**: `$app/state` の `page.url.searchParams.has('about')` で about モードを導出。**`$effect` で変化を検知 → `morphText` で greeting↔title を内容 morph**。`+page.ts` の load 追加は不要。
4. **transition.ts**: toggle 分岐は「VT をスキップして return」だけに痩せる。**`onNavigate` の Promise ハンドシェイク（morph 完了まで差し替えを待たせる）は不要**——DOM が破棄されないので「差し替えの瞬間」自体が存在しない。
5. **morphText にキャンセル機構**: 連打・逆方向切替で `$effect` が再実行されたら、進行中の morph を中断してから新 morph を開始。
6. **戻り導線**: `nav.svelte.ts` の from / Focus 戻りリンクは `/?about#id` 形式（query と hash は共存可）。
7. **既知のトレードオフ（仕様化）**: `?about` はプリレンダされない → 直リンクで開くと挨拶状態の HTML が出てハイドレーション後に about へ。これは**greeting→title の morph を入場演出として意図的に再生**することで「ちらつき」を仕様に変える。
8. **前回中断分の残タスクも同時に消化**: `app.css`（`.intro-caption-card` スタイル定義、旧 `.text-caption` / `::view-transition-*(intro-caption)` ルール掃除、About 右上カード入場の CSS マウントアニメ化）、`scramble.ts` 削除、`pnpm check` / `build` 実行。
