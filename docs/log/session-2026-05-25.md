## 本当の理由 — catalog の用途を取り違えていた

ユーザーから明示された catalog の本来の目的は **3 つ**:

1. **既存実装の棚卸・リファクタ** (= 雑に作った generate-theme / prompt / 規約を整える)
2. **現状で実現不可能な表現の洗い出し** (= 今の枠だと描けないものを特定する)
3. **次の表現を引き出すための情報整理** (= prompt や規約に必要な語彙・参考を確立する)

つまり catalog は **Claude の前に置く "選ばせる枠" ではなく、設計者 (私たち) のための
診断ツール**。Claude に渡す材料を整えるための棚。

### 私が誤っていたこと

| 私の思い込み | 本当のところ |
|---|---|
| catalog = Claude が選ぶメニュー | catalog = **設計者が現状を点検するための棚** |
| 議論の軸 = 「自由度 vs 縛り」 | 議論の軸 = **「今あるものを点検・整える」** |
| 次にやるべきは新機構の追加 | 次にやるべきは **棚卸・ギャップ確認・補助情報整理** |
| 「適切性ファースト」= 機構の常駐有無 | 「適切性ファースト」= **点検 / リファクタを経ずに足す こと自体への抵抗** |

B1 が通った本当の理由も「常駐するかどうか」ではなく、たぶん
「OGP の設計はすでに通っていて、他の B/D/E は catalog 3 用途 (棚卸・ギャップ・補助情報) を
経ていない状態だったから保留にされた」が近い。

### 一番の根本

私は **保険的な思考** (= 自由生成は壊れるから枠を作ろう) で catalog を理解した。
でもこのプロジェクトは **「非決定性は仕様」** を掲げている。

ここに私の思考とプロジェクト精神の最大のズレがある:

- 私は「壊れない仕組みを作る」をデフォルトとする (= 安全マージン思考)
- プロジェクトは「壊れて当然、壊れ方を整える」を許容する (= 非決定性受容)

「自由度は正義」と言われたのは、私の保険的思考の **構造そのもの** を見直せ、という指摘。

## これから何をやると良いか

### 0. リサーチ (先にやる)

棚卸の前に、外の世界を見て自分の語彙を増やす:

- **表現カタログ系の事例調査**: 既存の「Web デザイン表現を分類した記事 / サイト / リポ」
  (例: Awwwards の categorization, Brutalist 系まとめ, CSS Tricks 等)
- **最新の良い表現・デザイン設計の動向**: 2025-2026 周辺の Web デザイン傾向、
  個人サイトの先鋭的事例、AI と組み合わせた表現の試み
- **`DESIGN.md` のような設計ドキュメント慣習**: プロジェクトの "顔" を言語化する
  方法、design system のドキュメント実践例 (Storybook の手前の話)

### 1. 棚卸・リファクタ

リサーチで得た語彙を持って、現状の generate-theme.ts / system prompt / theme.css
規約 / Footer / Base.astro 等を読み返し、雑な箇所・矛盾・改善点を洗い出す。

### 2. ギャップ確認

catalog の各カテゴリと現状の枠を照合し、「**今の実装では描けないもの**」を特定する。
「機構が要る」「prompt が要る」「規約緩和が要る」を分類。

### 3. 補助情報の確立

system prompt の改善、必要なら techniques 系 md の整備、参考例の整理。

### 4. その先に (もし必要なら)

棚卸 + ギャップ + 補助情報整理を経て、本当に必要と判明した機構だけを追加する。
